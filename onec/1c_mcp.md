# Базовый слой MCP: форк vladimir-kharin/1c_mcp

Upstream: https://github.com/vladimir-kharin/1c_mcp, пин — коммит `5abe316`
(после него только смотреть `git log`, обновляться осознанно).
Версии на пине: расширение `MCP_Сервер` 1.6.1, прокси 1.6.1, MCP SDK `>=1.8.0,<2.0.0`.

## Что берём как есть (не форкаем, не правим)

- **CFE-ядро** `build/MCP_Сервер.cfe` — ставится бинарником из апстрима:
  HTTP-сервис `mcp_APIBackend` (RootURL `mcp`: `GET /health`, `POST /rpc`,
  `/*` под Streamable HTTP), диспетчер, кеши, мета-инструменты
  (`list_metadata_objects`, `get_metadata_structure`), обработка управления.
- **Python-прокси** `src/py_server` — транспорт Streamable HTTP + per-user OAuth2
  (Authorization Code + PKCE, password grant удалён). Зависимости:
  `fastapi`, `uvicorn[standard]`, `httpx`, `pydantic>=2.5`, `pydantic-settings`,
  `python-dotenv`, `mcp>=1.8.0,<2.0.0`. Python 3.11+, Docker-файл в комплекте.
- Требования: платформа 1С **8.3.20+** (у расширения `CompatibilityMode Version8_3_20`).

## Что пишем сами

- **`onec/ext/`** — наше расширение `A1C_Инструменты` (префикс `a1c_`) с доменными
  read-only инструментами. Механика discovery ядра
  (`mcp_Метаданные.ПереопределяемыеКорневыеПодсистемы` +
  `СоставПодсистемыВключаяПереопределения`), проверена по исходникам:
  корневая подсистема ищется по ВХОЖДЕНИЮ `mcp_MCPСервер` в имя
  (наша — `a1c_mcp_MCPСервер`), а дочерняя подсистема контейнеров — по ТОЧНОМУ
  имени `mcp_КонтейнерыИнструментов` внутри каждого найденного корня
  (поэтому она у нас БЕЗ префикса — одинаковость имён между расширениями здесь
  задумана, это «переопределение», а не конфликт). Обработки-контейнеры —
  с префиксом `a1c_`, имена произвольные. Обработчики вызывают
  `mcp_Метаданные.*` ядра для описания схем (кросс-вызовы расширений —
  штатный паттерн из agents.md).
- **`backend/src/app/onec/`** — MCP-клиент бэкенда к прокси (тот же `mcp` SDK).
- **`onec/smoke_check.py`** — stdlib-проверка 1С-стороны без прокси (прямой
  JSON-RPC в `/hs/mcp/rpc`).

## Ключевые факты интеграции

- Endpoints 1С: `GET {base}/hs/mcp/rpc` — нет; правильно: `GET {base}/hs/mcp/health`,
  `POST {base}/hs/mcp/rpc` (JSON-RPC, методы `tools/list`, `tools/call`, ...).
- Прокси: `GET /health`, `POST /mcp/` (Streamable HTTP), `GET /sse` (legacy).
  Env: `MCP_ONEC_URL`, `MCP_ONEC_SERVICE_ROOT=mcp` (дефолт), `MCP_AUTH_MODE=none|oauth2`.
- Регистр имени базы в URL = регистру публикации, иначе редирект роняет POST в GET.
- Паттерн инструмента: обработка в подсистеме контейнеров + два экспортных метода
  `ДобавитьИнструменты(Инструменты)` / `ВыполнитьИнструмент(ИмяИнструмента, Аргументы)`;
  возврат — строка / массив структур / структура `{type, text}`.
- Стиль BSL ядра: табуляция, `#Область`, ошибки через `ВызватьИсключение`.

## Безопасность (проверено по исходникам)

- Роль `mcp_ОсновнаяРоль` ядра НЕ даёт прав на данные (только режимы окна +
  скрытие подсистем из интерфейса). Доступ к данным идёт по ролям вызывающего
  пользователя — RLS и профили КА2 применяются платформой нативно.
- Наше расширение ролей не содержит вообще: прав не добавляет, только код.
  Read-only держится тремя слоями (см. AGENTS.md): только читающие инструменты
  + read-only профили пользователей 1С + аудит.
- Перед публикацией сверить `tools/list` с ожидаемым составом (ядро отдаёт
  мета-инструменты — они read-only, оставляем осознанно).

## Состав нашего расширения (v0.2.0)

- `a1c_ИнструментОстатки` — `get_stock_balance` (ТоварыНаСкладах).
- `a1c_ИнструментКонтрагенты` — `get_counterparty` (Контрагенты + долг из РасчетыСКлиентами).
- `a1c_ИнструментОтчеты` — `run_skd_report` (`sales_by_warehouse` по РеализацияТоваровУслуг, `debtors` по РасчетыСКлиентами).
- `a1c_ИнструментЗапросы` — универсальные `execute_select` (только ВЫБРАТЬ/SELECT + кап строк) и `validate_query` (пробное выполнение ПЕРВЫЕ 1, вердикт строкой).
- `a1c_АгентДоступ` — роль: только Использование HTTP-сервиса ядра.

## Сверенные метаданные КА2 (пилот, из source-MCP пользователя)

- `ТоварыНаСкладах`: ресурс количества — **`ВНаличии`** (`ВНаличииОстаток`), есть `КОтгрузке`.
- `РасчетыСКлиентами`: `Контрагент` — ТОЛЬКО через `АналитикаУчетаПоПартнерам.Контрагент`;
  ресурсы `Сумма`/`КОплате`/`Оплачивается`/`Отгружается`.
- `Контрагенты`: `ИНН`, `НаименованиеПолное`, `Партнер` — всё есть.
- `Склады` — иерархический (`ЭтоГруппа`): фильтр только по элементам.
- `РеализацияТоваровУслуг`: шапка `Склад`/`Дата`, ТЧ `Товары` (`Номенклатура`, `Количество`, `Сумма`).
- Нерешённое: падение `get_counterparty` в `УстановкаПараметровСеанса` БСП
  (разовое? повторилось — проверять связку пользователя `agent` со справочником
  Пользователи и базовые права на чтение пользователей).

## Осознанные отклонения v1

- Отчёты реализованы **запросами в BSL**, а не макетами СКД: контракт инструмента
  (`run_skd_report` + типизированные параметры) тот же, рисков XML/DSС-движка
  меньше, отладка по логам пользователя проще. Переход на макеты СКД
  (скил `skd-compile`) — когда понадобятся пользовательские настройки/раскладки.
- Форк на GitHub не заводим, пока не понадобится править ядро: пин коммита выше,
  `.cfe` берётся из апстрима. Понадобится патч — форкаем тогда.
