# Базовый слой MCP: форк vladimir-kharin/1c_mcp

Upstream: https://github.com/vladimir-kharin/1c_mcp, пин — коммит `5abe316`
(после него только смотреть `git log`, обновляться осознанно).
Чек-аут лежит сабмодулем в `onec/1c_mcp/` (после клона: `git submodule update --init`);
compose-сервис `mcp-proxy` собирается из него (`build: ./onec/1c_mcp`).
Версии на пине: расширение `MCP_Сервер` 1.6.1, прокси 1.6.1, MCP SDK `>=1.8.0,<2.0.0`.

## Что берём как есть (не форкаем, не правим)

- **CFE-ядро** `build/MCP_Сервер.cfe` — ставится бинарником из апстрима:
  HTTP-сервис `mcp_APIBackend` (RootURL `mcp`: `GET /health`, `POST /rpc`,
  `/*` под Streamable HTTP), диспетчер, кеши, мета-инструменты
  (`list_metadata_objects`, `get_metadata_structure`), обработка управления.
- **Python-прокси** `src/py_server` — транспорт Streamable HTTP + per-user OAuth2
  (Authorization Code + PKCE, password grant удалён). Зависимости:
  `fastapi`, `uvicorn[standard]`, `httpx`, `pydantic>=2.5`, `pydantic-settings`,
  `python-dotenv`, `mcp>=1.8.0,<2.0.0`. Python 3.11+, Docker-файл в комплекте.
- Требования: платформа 1С **8.3.20+** (у расширения `CompatibilityMode Version8_3_20`).

## Что пишем сами

- **`onec/ext/`** — наше расширение `A1C_Инструменты` (префикс `a1c_`) с доменными
  read-only инструментами. Механика discovery ядра
  (`mcp_Метаданные.ПереопределяемыеКорневыеПодсистемы` +
  `СоставПодсистемыВключаяПереопределения`), проверена по исходникам:
  корневая подсистема ищется по ВХОЖДЕНИЮ `mcp_MCPСервер` в имя
  (наша — `a1c_mcp_MCPСервер`), а дочерняя подсистема контейнеров — по ТОЧНОМУ
  имени `mcp_КонтейнерыИнструментов` внутри каждого найденного корня
  (поэтому она у нас БЕЗ префикса — одинаковость имён между расширениями здесь
  задумана, это «переопределение», а не конфликт). Обработки-контейнеры —
  с префиксом `a1c_`, имена произвольные. Обработчики вызывают
  `mcp_Метаданные.*` ядра для описания схем (кросс-вызовы расширений —
  штатный паттерн из agents.md).
- **`backend/src/app/onec/`** — MCP-клиент бэкенда к прокси (тот же `mcp` SDK).
- **`onec/smoke_check.py`** — stdlib-проверка 1С-стороны без прокси (прямой
  JSON-RPC в `/hs/mcp/rpc`).

## Ключевые факты интеграции

- Endpoints 1С: `GET {base}/hs/mcp/rpc` — нет; правильно: `GET {base}/hs/mcp/health`,
  `POST {base}/hs/mcp/rpc` (JSON-RPC, методы `tools/list`, `tools/call`, ...).
- Прокси: `GET /health`, `POST /mcp/` (Streamable HTTP), `GET /sse` (legacy).
  Env: `MCP_ONEC_URL`, `MCP_ONEC_SERVICE_ROOT=mcp` (дефолт), `MCP_AUTH_MODE=none|oauth2`.
- Регистр имени базы в URL = регистру публикации, иначе редирект роняет POST в GET.
- Паттерн инструмента: обработка в подсистеме контейнеров + два экспортных метода
  `ДобавитьИнструменты(Инструменты)` / `ВыполнитьИнструмент(ИмяИнструмента, Аргументы)`;
  возврат — строка / массив структур / структура `{type, text}`.
- Стиль BSL ядра: табуляция, `#Область`, ошибки через `ВызватьИсключение`.

## Безопасность (проверено по исходникам)

- Роль `mcp_ОсновнаяРоль` ядра НЕ даёт прав на данные (только режимы окна +
  скрытие подсистем из интерфейса). Доступ к данным идёт по ролям вызывающего
  пользователя — RLS и профили КА2 применяются платформой нативно.
- Наше расширение ролей не содержит вообще: прав не добавляет, только код.
  Read-only держится тремя слоями (см. AGENTS.md): только читающие инструменты
  + read-only профили пользователей 1С + аудит.
- Перед публикацией сверить `tools/list` с ожидаемым составом (ядро отдаёт
  мета-инструменты — они read-only, оставляем осознанно).

## Состав нашего расширения

- `a1c_ИнструментОстатки` — `get_stock_balance` (ТоварыНаСкладах).
- `a1c_ИнструментКонтрагенты` — `get_counterparty` (Контрагенты + долг из РасчетыСКлиентами).
- `a1c_ИнструментОтчеты` — `run_skd_report` (`sales_by_warehouse` по РеализацияТоваровУслуг, `debtors` по РасчетыСКлиентами).
- `a1c_ИнструментЗапросы` — универсальные `execute_select` (только ВЫБРАТЬ/SELECT + кап строк), `execute_query` (&параметры, feenlace) и `validate_query` (пробное выполнение ПЕРВЫЕ 1, вердикт строкой).
- `a1c_ИнструментДерево` — `get_metadata_tree`, `get_object_structure`, `get_configuration_info` (имя/версия/поставщик/платформа/режим ИБ; feenlace/mcp-1c, MIT).
- `a1c_ИнструментЖурнал` — `get_event_log` (feenlace; в файловом режиме заглушка с подсказкой).
- `a1c_ИнструментНавигация` — `get_object_by_link`, `get_link_of_object`, `find_references_to_object` (OneBridge/thmoscow-byte, MIT).
- `a1c_ИнструментПрава` — `get_access_rights` (OneBridge). **Синтаксис починен (`2064243`),
  но сама логика — заглушка:** возвращает жёсткий список прав и `isAdmin = Ложь`
  независимо от ролей пользователя. Опираться на ответ как на реальные права нельзя
  (см. `TODO.md`).
- `a1c_АгентДоступ` — роль: только Использование HTTP-сервиса ядра.
- Референсные выгрузки чужих MCP лежат в `data/` (в git не коммитятся).

## Правила добавления обработки (грабли сентября 2026)

- Новая обработка обязательно вписывается в `Configuration.xml` (ChildObjects)
  и в Content `mcp_КонтейнерыИнструментов` — иначе «Неизвестный объект метаданных».
- UUID объекта + `TypeId`/`ValueId` в дескрипторе — всегда свежие уникальные
  (копия из соседнего файла даёт «содержит не уникальное значение»).
- Один битый контейнер роняет **весь** `tools/list` ядра (обход без `Попытка`),
  включая ядерные тулзы; симптом — 500 на всё. Диагностика: Технологический
  журнал (`Exception` → модуль/строка); бисекция — убрать контейнер из Content.
- Смешанные кириллица/латиница в идентификаторах (`Аргуuments`) — «Переменная
  не определена»; дизайнерские варнинги про `mcp_Метаданные` из другого
  расширения — норма, кросс-вызовы работают в рантайме.
- **`Новый Массив(...)` с аргументами недопустим** — конструктор `Массив` не
  принимает параметров: «Ошибка при вызове конструктора (Массив)». Список собирается
  явно: `Новый Массив; Список.Добавить(...)`. Поймано в двух наших модулях
  (`a1c_ИнструментПрава`, `a1c_ИнструментДерево`) — см. коммит `2064243`.

## Особенности языка запросов (проверено пробами на живой КА 2.5.22, 11 проб)

Проверено прямыми JSON-RPC-вызовами `execute_select` — не догадками, а замерами:

- **`ПЕРВЫЕ` — только сразу после `ВЫБРАТЬ`.** После имени таблицы — синтаксическая
  ошибка `"ПЕРВЫЕ"`. Верно: `ВЫБРАТЬ ПЕРВЫЕ 10 Поле ИЗ Таблица`.
- **Подсчёт строк — `СУММА(1) КАК КЗ`.** `СЧЁТЧИК(*)`, `СЧЁТЧИК(Ссылка)`,
  `ПОДСЧИТАТЬ(1)`, `ПОДСЧИТАТЬ(*)` — синтаксическая ошибка на позиции имени
  функции. `МИНИМУМ/МАКСИМУМ/СУММА` с литералом или полем работают.
  Проверено: `ВЫБРАТЬ СУММА(1) КАК КЗ ИЗ <справочник>` вернул 1033 строки.
- **`СГРУППИРОВАТЬ ПО` — с буквой «С».** Без неё — ошибка `"ПО"`. Работает в паре
  с `СУММА(1)`: разбивка по статусам дала 998 «Действует» / 35 «Закрыт».
- **Переводы строк и табуляция разрешены** — многострочный запрос выполняется,
  ломает только неверное положение конструкций.
- **Незаполненное поле — `ГДЕ <Поле> ЕСТЬ NULL`.** `ЕСТЬ НЕОПРЕДЕЛЕНО` не
  поддерживается: ошибка `"ЕСТЬ"`.
- **Перечисления не фильтруются ни строкой, ни полным именем.**
  `ГДЕ Статус = "Действует"` → пусто (0 строк), хотя таких 998.
  `Статус = Перечисления.СтатусыДоговоровКонтрагентов.Действует` → «Поле не найдено».
  `ЗНАЧЕНИЕ(Перечисления...)` → «Неверные параметры». Единственный путь узнать
  значения — `СГРУППИРОВАТЬ ПО <Поле>`; отбор по перечислению невозможен.
- **`&параметр` со строкой для перечисления не помогает:** `execute_query` с
  `{"Статус": "Действует"}` вернул пусто.

## Реальные имена в КА 2.5.22 (не совпадают с формулировками ТЗ)

- Справочники: `Справочник.ДоговорыКонтрагентов` (синоним «Договоры с контрагентами»),
  `Справочник.Контрагенты`.
- **Есть:** `Менеджер`, `Статус`, `ТипДоговора` (Закупка / Реализация / Передача на
  комиссию), `ДатаОкончанияДействия`, `Контрагент`, `Номер`, `Дата`, `Наименование`,
  `НаименованиеПолное`, `ЮридическоеФизическоеЛицо`.
- **Нет:** `РабочееНаименование`, `ТекущееСостояние`, `СрокДействия`, `ВидДоговора`
  (есть `ТипДоговора`), `ВидКонтрагента`.
- Значения: статус = Действует / Закрыт; пустая дата окончания = `ДАТАВРЕМЯ(1,1,1)`
  (бессрочный), таких 932 из 1033.
- Общий урок: имена реквизитов и допустимые значения — только из
  `get_metadata_structure` / группировок, формулировки ТЗ модели подсказывать нельзя.
  `get_metadata_structure` на больших справочниках отдаёт ~10 КБ и обрезается в
  логе петли — читать его целиком неудобно.

## Сверенные метаданные КА2 (пилот, из source-MCP пользователя)

- `ТоварыНаСкладах`: ресурс количества — **`ВНаличии`** (`ВНаличииОстаток`), есть `КОтгрузке`.
- `РасчетыСКлиентами`: `Контрагент` — ТОЛЬКО через `АналитикаУчетаПоПартнерам.Контрагент`;
  ресурсы `Сумма`/`КОплате`/`Оплачивается`/`Отгружается`.
- `Контрагенты`: `ИНН`, `НаименованиеПолное`, `Партнер` — всё есть.
- `Склады` — иерархический (`ЭтоГруппа`): фильтр только по элементам.
- `РеализацияТоваровУслуг`: шапка `Склад`/`Дата`, ТЧ `Товары` (`Номенклатура`, `Количество`, `Сумма`).
- Нерешённое: падение `get_counterparty` в `УстановкаПараметровСеанса` БСП
  (разовое? повторилось — проверять связку пользователя `agent` со справочником
  Пользователи и базовые права на чтение пользователей).

## Статус пилота (живая КА2, 2026-09-13)

End-to-end работает: ~18 инструментов в `tools/list` (курируемые + ядерные
мета-инструменты + заимствованные feenlace/OneBridge), реальные данные JSON

  в текстовый блок как есть, а массивы/структуры портит через `Строка()`
  (массив структур приезжает как «Структура» × N без значений).

  `backend/scripts/smoke_tools.py --replay backend/tests/fixtures/ka2_pilot.json`

## Осознанные отклонения v1

- Отчёты реализованы **запросами в BSL**, а не макетами СКД: контракт инструмента
  (`run_skd_report` + типизированные параметры) тот же, рисков XML/DSС-движка
  меньше, отладка по логам пользователя проще. Переход на макеты СКД
  (скил `skd-compile`) — когда понадобятся пользовательские настройки/раскладки.
- Форк на GitHub не заводим, пока не понадобится править ядро: пин коммита выше,
  `.cfe` берётся из апстрима. Понадобится патч — форкаем тогда.
