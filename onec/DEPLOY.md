# Деплой 1С-стороны на тестовую VM (выполняет владелец базы)

Роли: ты — руки на Windows-VM с тестовой КА2; я правлю код по логам.
Присылай полные выводы команд текстом (не скриншотами).

## 0. Что нужно

- Платформа 1С:Предприятие **8.3.20+**, тестовая база КА2 (можно копия боевой).
- Опубликованный веб-сервер (IIS/Apache) — публикация делается ниже.
- Python 3.11+ на VM (для `smoke_check.py` и позже прокси). Зависимости НЕ нужны.

## 1. Базовое расширение MCP_Сервер (ядро, чужой код)

1. Скачай `MCP_Сервер.cfe` из апстрима: https://github.com/vladimir-kharin/1c_mcp
   (каталог `build/` на коммите из `onec/1c_mcp.md`, либо свежий Releases).
2. Конфигуратор тестовой базы → Администрирование → Расширения конфигурации →
   Добавить → выбрать `.cfe` → обновить базу.
3. В результате в расширении должен быть HTTP-сервис `mcp_APIBackend`.

## 2. Наше расширение A1C_Инструменты (наш код, `onec/ext/`)

1. Скопируй каталог `onec/ext/` из этого репозитория на VM.
2. Конфигуратор → Расширения конфигурации → Добавить → **загрузить из файлов**,
   указав каталог `onec/ext/` → обновить базу.
3. Если загрузка ругается — ничего не чини сам, пришли мне ПОЛНЫЙ текст ошибки:
   допилю XML и пришлю обновлённый `onec/ext/`.
4. Запасной путь (если загрузка из файлов упрётся): создай расширение и восемь
   обработок (`a1c_ИнструментОстатки`, `a1c_ИнструментКонтрагенты`,
   `a1c_ИнструментОтчеты`, `a1c_ИнструментЗапросы`, `a1c_ИнструментДерево`,
   `a1c_ИнструментЖурнал`, `a1c_ИнструментНавигация`, `a1c_ИнструментПрава`)
   вручную в конфигураторе, BSL модулей менеджера возьми из
   `onec/ext/DataProcessors/*/Ext/ManagerModule.bsl`, подсистему
   `a1c_mcp_MCPСервер` с контейнерами собери по образцу `onec/ext/Subsystems/`.
   Каждую новую обработку также впиши в `Configuration.xml` (ChildObjects)
   и в Content `mcp_КонтейнерыИнструментов`, UUID/`TypeId`/`ValueId` — новые
   уникальные (копия из соседнего файла даёт «содержит не уникальное значение»).
   Поток правок — строго в одну сторону: правим XML/BSL в git → заливаем
   в базу из файлов. Дамп из базы в репозиторий запрещён без посимвольного
   ревью diff (иначе затирает фиксы несвежим состоянием базы, как было
   с `Аргуuments` в коммите `6168597`).

## 3. Публикация HTTP-сервиса

Администрирование → Публикация на веб-сервере: опубликовать базу,
имя публикации — каким будешь ходить (например `ka2test`).
**Регистр букв в URL обязан совпадать с именем публикации** — иначе 1С делает
редирект и POST превращается в GET (проверено по докам апстрима).

### 3.1. JWT-аутентификация (per-user RLS, prod)

Для per-user RLS бэкенд передаёт Bearer-JWT в `{base_url}/hs/mcp/rpc`;
1С проверяет подпись и ставит `ТекущийПользователь` по `sub`.
Требуется платформа **8.3.21+**.

В файле публикации (`default.vrd`) секция `<accessTokenAuthentication>` должна
висеть на **HTTP-сервисе**, а не на веб-сервисе: MCP-ядро — это HTTP-сервис
`mcp_APIBackend` (RootURL `mcp`), поэтому блок идёт в `<httpServices>`.
Секция внутри `<ws>/<point>` для него НЕ действует (токен платформа не видит,
запрос падает «Идентификация пользователя в информационной базе не выполнена»):

```xml
<httpServices>
    <service name="mcp_APIBackend"
            rootUrl="mcp"
            enable="true"
            reuseSessions="autouse"
            sessionMaxAge="1200"
            poolSize="10"
            poolTimeout="5">
        <accessTokenAuthentication>
            <accessTokenRecepientName>mcp</accessTokenRecepientName>
            <issuers>
                <issuer name="1c-ai-chat"
                        authenticationClaimName="sub"
                        authenticationUserPropertyName="name"
                        keyInformation="YnSdgu3G2xglYfpT3eLee2Sz1M+VwqqxkL7XYu9fP5c="/>
            </issuers>
        </accessTokenAuthentication>
    </service>
</httpServices>
```

- `name`/`rootUrl` — имя HTTP-сервиса и его RootURL в метаданных (`mcp_APIBackend`/`mcp`).
- `accessTokenRecepientName` = `mcp` — значение, которое BSL кладёт в `Токен.Получатели`.
- `issuer name` = `1c-ai-chat` (совпадает с `iss` в токене, генерируется BSL).
- `authenticationClaimName` = `sub` — поле токена с именем пользователя.
- `authenticationUserPropertyName` = `name` — свойство элемента Пользователи.
- `keyInformation` — Base64-ключ HS256 (тот же, что в BSL `КлючПодписиТокена()`
  и в `.env` бэкенда `JWT_SECRET`).

**Обязательный claim `exp`:** платформа (проверено на 8.3.27) при
`accessTokenAuthentication` требует в токене `exp`; без него запрос падает
`HTTP 402 / Claim not found exp`. BSL обязан задавать `Токен.ВремяЖизни`
(в `a1c_ЧатФоновый.СформироватьТокенДоступа()` — 28800 сек = 8 часов).

После правки `default.vrd` — **перезапустить веб-сервер** (IIS: `iisreset`,
Apache: `systemctl restart apache2`).

Dev-режим (`JWT_SECRET` пуст) не требует этой секции — бэкенд ходит Basic auth
под `ONEC_USERNAME`.

## 4. Пользователь для агента (read-only)

Отдельный пользователь 1С, БЕЗ административных прав. Ему нужно:

1. Роль **`a1c_АгентДоступ`** из нашего расширения — даёт только Использование
   HTTP-сервиса ядра. Назначать **в конфигураторе** (свойства пользователя),
   НЕ через режим Предприятие — иначе не взлетит (особенность ролей расширений).
2. **Элемент справочника Пользователи**, привязанный к пользователю ИБ
   (Администрирование → Настройки пользователей и прав → Пользователи).
   Без него БСП не ставит параметр сеанса `ТекущийПользователь` и падает
   ПЕРВОЕ ЖЕ обращение к данным: `Пользователь "agent" не существует
   в справочнике "Пользователи"`. Мета-инструментам это не мешает (данных
   не касаются) — поэтому tools/list работает, а запросы падают.
3. Группы доступа с правом **Чтение** (только чтение!) на объекты инструментов:
   `ТоварыНаСкладах`, `РасчетыСКлиентами`, `Контрагенты`, `Партнеры`,
   `Склады`, `Номенклатура`, `РеализацияТоваровУслуг`.
   Без чтения платформа отвечает `Ошибка в ограничении доступа к данным.
   объект: '...'; право: 'Чтение'` — объект и право называются прямо в тексте.
   Прав на данные наше расширение не добавляет — доступ идёт по ролям
   пользователя (RLS платформы). Полные права НЕ давать даже «для проверки».

Проверка, что право легло: в конфигураторе открой роль `a1c_АгентДоступ` —
на HTTP-сервисе `mcp_APIBackend` (шаблоны `rpc`, `health`) должны стоять галки
Использование. Если их нет — поставь вручную в конфигураторе и сообщи мне.

## 5. Смоук (пришли мне весь вывод)

```bat
python onec\smoke_check.py --url http://HOST/ka2test --user AGENT_USER
```

Ожидается: health 200, в `tools/list` есть `get_stock_balance`,
`get_counterparty`, `run_skd_report`, `execute_select`/`execute_query`,
`get_metadata_tree`, `get_configuration_info`, `get_event_log`, навигация
(`get_object_by_link`, …) и `get_access_rights`, три `tools/call` без FAIL.
Пароль спросит интерактивно (или `--password`, но тогда он останется в истории).

(всё зашито, запуск без параметров).

## 6. Сверка метаданных (пришли вывод)

Имена объектов в твоей КА2 могут отличаться от моих предположений
(ТоварыНаСкладах, Контрагенты/Партнеры, РеализацияТоваровУслуг,


Пришли ВЕСЬ вывод: по нему поправлю запросы в BSL под твою базу.

## 7. Прокси и чат (локальный контур)

Сети VPS↔VM нет — всё крутится на Windows-машине. Полная инструкция:
[`CHAT.md`](CHAT.md) (бэкенд + postgres локально; основной путь — прямые вызовы
в `{base_url}/hs/mcp/rpc` под `ONEC_USERNAME`/`ONEC_PASSWORD`, прокси — только
для штатного пути без `base_url`, `ONEC_MODE=live`).

Чат в базе: Все функции → Обработки → `a1c_Чат`. В поле «Бэкенд» —
адрес локального бэкенда (`http://localhost:8000`). При открытии форма молча
проверяет себя (`GET /tools?base_name=&base_url=`): неуспех — жёлтый баннер
`ПредупреждениеБазы` с адресом и причиной, форма работает дальше.

Смоук live-связки (каталог `backend`): `uv run python scripts/smoke_tools.py --live`.

## Troubleshooting

- Баннер «Агент недоступен для этой базы» при открытии чата — startup-check
  (`GET /tools?base_name=&base_url=`) не прошёл: в скобках адрес и причина.
  `400` с «проверьте адрес публикации» — база шлёт `base_name` без `base_url`
  (файловая ИБ?) и её нет в `ONEC_BASES`; транспортная ошибка — нет сети
  бэкенд→1С или неверные `ONEC_USERNAME`/`ONEC_PASSWORD`.
- `HTTP 403 Недостаточно прав...` — у пользователя нет Использования на методы
  HTTP-сервиса. Лечится шагом 4 (роль `a1c_АгентДоступ` в конфигураторе).
  Проверка диагноза: временно дай пользователю полные права — если health
  вернул 200, дело точно в правах (полные сразу убери). Также глянь
  «Активные пользователи» во время запроса: убедись, что стучится именно
  `agent`, а не пользователь, зашитый в default.vrd.
- `HTTP 401/403` — неверный пользователь/пароль или у пользователя нет прав
  на данные (RLS тоже может резать — проверь тем же пользователем интерактивно).
- `HTTP 401` при per-user RLS (JWT) — проверь: (а) секция `<accessTokenAuthentication>`
  есть в `default.vrd` и веб-сервер перезапущен; (б) ключ `keyInformation` совпадает
  с `JWT_SECRET` бэкенда и BSL `КлючПодписиТокена()`; (в) у пользователя есть элемент
  в справочнике Пользователи с `name` = `sub` из токена + роль `a1c_АгентДоступ`.
- HTML вместо JSON / `POST превратился в GET` — регистр имени базы в URL.
- `Extension ... cannot be loaded` — пришли текст ошибки целиком.
- Пустые массивы в ответах при живых данных — возможно RLS пользователя:
  сравни с тем, что видит этот пользователь в тонком клиенте.
- `Неизвестный объект метаданных - DataProcessor.a1c_...` при загрузке —
  обработка не вписана в `Configuration.xml` (ChildObjects): добавь и перезалей.
- `...содержит не уникальное значение` (`TypeId`/`ValueId`) — дескриптор
  скопирован из соседнего файла: сгенерируй свежие UUID.
- 500 на **все** `tools/list`/`tools/call`, включая ядерные (`id: null` или пустое
  тело) — падает обход контейнеров диспетчером (там нет `Попытка`): смотри
  Технологический журнал по времени запроса (`Exception` → модуль/строка),
  чини первый названный контейнер, перезалей расширение, перезапусти службу 1С.
  Быстрая локализация — временно убрать подозреваемый контейнер из Content
  `mcp_КонтейнерыИнструментов`.
- JSON-RPC `-32603` + «Непредвиденный символ при чтении JSON», `id: null` —
  битое тело запроса (экранирование кавычек в PowerShell/curl), сервер ни при чём:
  собирай JSON через `ConvertTo-Json` или бери готовый `onec/test_rpc.ps1`.
- PS-скрипты с кириллицей: файлы обязаны быть в UTF-8 **с BOM**, иначе
  PowerShell 5.1 читает их как Windows-1251 (кракозябры + `UnexpectedToken`).
